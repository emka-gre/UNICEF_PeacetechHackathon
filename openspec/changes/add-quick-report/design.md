## Context

See proposal.md for the motivation. Relevant current state of the hackathon build:

- The full form (`src/pages/Report.tsx`) already accepts a pre-fill (`ReportPrefill`: link, description) from the fact-check screen and skips the first step when one is given.
- Reports carry `origin: 'form' | 'fact-check'`. The server turns `fact-check` into a tag the dashboard shows.
- Reports are sent through the local queue (`src/lib/queue.ts`) to `POST /api/reports`, which is idempotent on the client UUID.
- The server already calls Claude for fact-checking (`server/factcheck.ts`) and gives labelled demo answers when no API key is set.
- The export only includes verified reports with research consent.
- The PWA manifest is generated by vite-plugin-pwa in `vite.config.ts`.

## Goals / Non-Goals

**Goals:**
- Reporting from the share menu takes at most two taps after choosing Laaha
- No new route for reports into the system: quick reports use the same queue, endpoint and storage
- Guessed values are always visible as guesses to staff and never reach exports unchecked

**Non-Goals:**
- Sharing image files through the share target (needs a POST share target handled in the service worker; possible follow-up)
- Automatic verification or rejection. Claude only suggests a category.

## Decisions

### 1. GET share target for links and text
The manifest gets `share_target: { action: '/quick', method: 'GET', params: { title: 'title', text: 'text', url: 'url' } }`. The `/quick` page reads the query string, pulls the first `https://` URL out of `url` or `text`, and then clears the query string with `history.replaceState` so the shared link is not left in the browser history.
- *Why*: GET needs no service worker code and works with the existing app shell. Most apps, including Instagram, share a post as a link in `text`, not `url`, so both are checked.
- *Alternative*: POST with `enctype: multipart/form-data` to accept screenshots directly. Requires intercepting the request in the service worker and handing files to the page. Deferred.

### 2. One quick report page, two entry points
`/quick` is a normal route. The share target opens it filled in; the home screen button opens it empty. Add details navigates to `/report` with the existing `ReportPrefill` state, extended with `images`.
- *Why*: iPhone support and a single screen to test. Reuses the pre-fill path the fact-check screen already uses.

### 3. Quick reports use the existing endpoint with `origin: 'quick'`
`ReportInput` gains `origin: 'quick'`, and for that origin `victim` and `category` may be missing. The server sets `mode: 'online'`, `victim: 'not-say'`, `category: 'Other'`, the platform from the link's hostname (a fixed map: instagram.com, reddit.com, facebook.com / fb.com, tiktok.com, x.com / twitter.com, wa.me / whatsapp.com), and adds the tag `auto-filled`.
- *Why*: keeps idempotency, the offline queue and the no-logging rule in one place. Platform from the domain is exact, so it does not need AI.
- *Alternative*: a separate `/api/quick-reports` endpoint. Rejected because it duplicates validation and storage for no gain.

### 4. Category suggestion on arrival, after saving
After the report is saved and the response is sent, the server calls Claude with the link, description and first screenshot, asking for exactly one of the online categories. The answer is matched against the list; anything else keeps "Other". The suggestion is stored in a `suggestedCategory` field and also written to `category`, and the `auto-filled` tag stays until a moderator confirms.
- *Why on arrival rather than when a moderator opens the report*: the queue then shows useful categories straight away, and the demo shows the full flow. The cost is one short Claude call per quick report.
- *Why after saving*: a slow or failed call never delays the user or loses a report.
- No web search is used for this call. It is a classification, not a fact-check.

### 5. Confirmation rule enforced on the server
`PATCH /api/staff/reports/:id` refuses `status: 'verified'` while the report has the `auto-filled` tag. The dashboard shows a "Confirm category" control that sets the category and removes the tag in one request. The stats endpoint leaves auto-filled reports out of the category counts.
- *Why on the server*: the consent and export rules are already enforced there, not only in the UI (see the foundation design).

## Risks / Trade-offs

- [Web share targets do not work on iPhone] → the home screen quick report button; mention "copy link, then open Laaha" in the guides.
- [The share menu shows "Laaha" even in discreet mode] → say so on the discreet-mode setting; a neutral installed name is a later option.
- [Shared URLs can carry tracking parameters that identify the sharer, e.g. Instagram's `igsh`] → strip query parameters from recognised platform links before saving.
- [Claude suggests the wrong category] → it is only a suggestion, visibly marked, and confirmation is required before verification or export.
- [Evidence sent to a third-party AI service] → the same exposure as the fact-check assistant; covered in the privacy notice; nothing is sent when no key is configured.
- [Quick reports lower the effort to send spam or duplicates] → moderators already review every report; duplicate links can be flagged in the queue later.
